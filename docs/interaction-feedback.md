# 通用提示词：请求态、禁用态与反馈

在优化后台管理页面或任何包含网络请求的交互时，优先把用户体验做完整，而不是只完成接口调用。请按以下原则实现：

- 所有会发起网络请求的操作都要有明确的 pending 状态，例如创建、保存、发布、刷新、重建索引、删除等。
- pending 状态应尽量精确到当前操作和当前资源，不要只用一个粗粒度的全局 `saving` 让页面所有按钮都无差别 loading。可以使用类似 `pendingAction = { name, sourceType, sourceId }` 的结构。
- 当前正在执行的按钮需要禁用并显示 loading，比如按钮内展示 `Spinner`，文案从“保存”变为“保存中...”。请求中应防止重复提交。
- 与当前请求冲突或危险的操作要适度禁用，例如保存中禁止关闭编辑弹窗，删除中禁止取消和重复确认，刷新中禁用刷新按钮。
- 列表项操作要只在当前项展示 loading，例如只让当前 FAQ 的发布、重建索引或删除按钮显示 spinner，不要让所有列表项一起闪动。
- 删除、覆盖、归档、重置等不可逆或高风险操作必须使用 shadcn/ui `AlertDialog` 做二次确认。弹窗文案要包含操作对象名称，并明确说明后果，例如“删除后无法恢复”。
- 表单弹窗保存时，保存成功前保持弹窗打开并展示 loading；保存和必要刷新完成后再关闭弹窗，避免用户看不到反馈。
- 错误提示使用 Sonner toast，不要在页面顶部插入 alert 挤占内容区域。失败 toast 优先展示接口返回的具体错误文案。
- 操作成功也应给简短 toast，例如“文章已保存”“FAQ 已发布”“索引已重建”“内容已删除”。不要为高频轻量操作加入过多干扰性的成功提示，按场景取舍。
- 区分主操作成功和副作用失败。例如“内容保存成功，但索引失败”不应该让保存接口整体失败；应保存内容、记录索引失败状态，并通过 badge 或错误信息展示索引状态。
- loading、disable 和 toast 逻辑应覆盖成功、失败和 finally 清理，确保请求失败后按钮能恢复可用。
- 所有图标按钮都要有清晰的 `aria-label` 和 `title`，例如“编辑 FAQ”“发布文章”“重建索引”“删除 FAQ”。
- 实现后要验证至少一个成功场景、一个失败场景和一个取消确认场景，并运行对应项目的 typecheck/lint。
